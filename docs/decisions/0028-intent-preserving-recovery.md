## Credential response ownership after reset

Ordinary authenticated responses and ordinary authentication failures never write or clear the credential cookie. Their captured request credentials may already have been replaced by an explicit reset when their response arrives; echoing the old token or clearing its cookie name can invalidate the replacement. PostgreSQL continues to resolve and touch the authenticated namespace under the existing real-clock inactivity predicate.

Only explicit new-session/bootstrap or reset may issue a fresh opaque HttpOnly, SameSite=Strict credential at Path=/api (Secure on secure requests). A valid existing-session bootstrap returns metadata without echoing its captured credential. A deliberate bootstrap with expired, malformed or duplicate unusable credentials creates a fresh isolated namespace; it does not revive the old one or accept caller-selected ownership. Ordinary malformed/expired requests remain401 without cookie mutation. This keeps explicit Resume usable without depending on a prior401 clearing a potentially newer credential.

The cookie has browser-session persistence rather than a fixed client Max-Age. The server remains authoritative for sliding24-hour inactivity, including active use beyond24 hours and rejection without revival after idle expiry. This avoids both an incorrect absolute browser24-hour deadline and out-of-order ordinary cookie-renewal writes. Closing a browser session may require explicit bootstrap; old in-memory intent remains a local draft, never price authority.

Actual HTTP regressions hold an authenticated success or pre-resolution guard across credential rotation and verify neither late response overwrites or clears the replacement. The local test database is separately owned; default reviewer data is preserved.
